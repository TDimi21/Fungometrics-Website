Root cause findings and limits
The exact route is POST /api/coach/add/players -> AddPlayers, under auth:sanctum,
ability:coach and route.scope. AddUserRequest.authorize returns true. No Gate or
player policy is called here. route.scope checks route parameters, not this body
team field. AddPlayers explicitly calls InvitationService.authorize BEFORE its
transaction/catch block. That method previously used message-less abort_unless
(active status AND role=coach AND CoachUtils::isCoachOnTeam, 403). Laravel renders
that HttpException as {"message":""}. This matches the reported denial shape.
The check was introduced/reused with invitation work, but it does NOT check
invitation/communications enable flags. Do not disable it to restore creation.

A separate capacity branch returns 403 code 016-LIMIT with a nonempty plan-limit
message. Ability failures use the existing 001-F response; unauthenticated uses
401/001-E. Those are distinct from the reported blank authorization exception.

Reproduced locally with real encrypted web cookie and Authorization: Bearer:
- active coach: GET /coach/teams 200; POST with membership UUID 403;
- inactive coach: GET /coach/teams 200; POST with real team UUID 403;
- active coach + correct team + cookie: POST 200, including with empty Bearer;
- empty Bearer without cookie: 401, NOT the reported blank 403.
Therefore empty Bearer alone is NOT the demonstrated root cause of the 403.
Production actor status and submitted team UUID were not provided/inspected;
which authorization predicate failed in production remains unverified. No
inactive account was reactivated and no missing relationship was invented.

Why the header was empty
Web login deliberately issues HttpOnly fmtrx_api_token and no JS bearer token.
getAuthToken consequently returns empty on normal cookie login. Three creation
forms built `Authorization: Bearer ${token}` unconditionally from a setup-time
snapshot. Other team reads use useAxiosAuth, which resolves a current legacy
token only when available, otherwise omits the header and uses credentials.
UseApiTokenCookie supplies the valid cookie token when bearerToken() is empty.
Cookie authentication is intended. Existing cookie flags/middleware and CSRF
configuration are unchanged; no authentication exception/bypass was added.

Team ID finding
Current /coach/teams route uses GetTeamsPlayersV2: id and id_team are BOTH team
UUIDs, with coach_team_id separate. The old GetTeamsPlayers controller returns
id=membership UUID and id_team=team UUID. Persisted older state can retain that
shape. HomeRoster used a destructured team snapshot plus team.id; Layout already
preferred id_team. New shared submission always resolves the current ref and
prefers id_team, falling back to a valid UUID id for direct team objects. It does
not translate unauthorized IDs on the server or weaken membership checks.
No stale production artifact is proven solely by this finding. Compare production
HEAD, current /coach/teams shape, submitted team value, loaded asset/manifest and
API origin privately before claiming a deployed mismatch is confirmed.
