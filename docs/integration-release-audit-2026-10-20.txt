PRIORITIZED FINDINGS

R01 HIGH — Offline planner writes can falsely report server success.
Evidence: mobile src/services/httpService.js:447-480 returns success=true,
source=queued with data={offline:true,offlineID}. plannerApi.js:108-121 passes
payload(res), which is undefined, into planFromApi's default object. pushPlan
therefore returns a truthy, EMPTY published plan. PlanBuilderScreen.js:276-289
merges that object over the real plan, clears pendingSync, and announces that
players and the web received it. Name, buckets and assigned IDs can be replaced
with blank/default values locally; server acceptance has not happened.
Player progress (plannerApi.js:147-160) and coach review (:201+) also reduce queued
success to true. PlayerWorkoutScreen.js:150-159 clears pendingSync and exits.
Executed actual plannerApi code with the transport's exact queued response:
  queuedRequestTreatedAsSaved=true
  returnedPlan.name="", buckets=[], assignedPlayerIds=[], no id
  queuedProgressTreatedAsSubmitted=true
No server/network writes were used for this reproduction.
Fix: distinguish queued/local/confirmed/failed results; never map an absent server
payload as a saved plan. Persist owner-bound pending edits until acknowledgement;
reconcile server version and canonical progress after replay. Apply to coach review
and unifiedPlannerApi.plannerRequest as well. Do not merely change the toast.
Acceptance: airplane-mode publish/finish/review must remain pending; reconnect
must create exactly one correct record and update both web and app.

R02 HIGH — Coach planner list and deletion are not server-integrated.
Evidence: DailyPlannerScreen.js:64-68 calls only listPlans/listTemplates.
plannerStore.js:101-124 reads/writes AsyncStorage; deletePlan never calls server.
The screen is registered in navigations/Stacks/MoreStack.js. Backend routes/api.php
has GET coach/daily-plans and DELETE coach/daily-plans/{id} (:379-381).
Impact: web-created/updated workouts need not appear in the mobile coach list;
Delete can remove only the phone's copy while players still have the assignment.
Fix: fetch and reconcile server collections, use authorized server deletion, retain
pending deletion offline, and enforce version/conflict handling. Templates/custom
drills are also local in this store; define shared-library parity explicitly.
Acceptance: create/edit/delete each direction with two devices and a web browser;
refresh and cold start must converge without silently overwriting newer edits.

R03 HIGH — Generic offline queue can discard or overwrite unsent work.
Evidence: httpService.js:281-329 prunes by age/capacity and uses unguarded
read/modify/write enqueue; :831-886 reads then replaces the queue on replay.
Non-429 failures are removed after three attempts. Authentication failures,
server outages and concurrent enqueue/replay can lose pending requests. An event
notification is not durable recovery. These are current static findings; a new
concurrency stress test was not run in this audit.
Fix: serialize owner/endpoint queue mutation and replay, stable operation IDs,
server idempotency, retained recoverable failures and an explicit sync-status UI.
Pause on authentication failure; do not silently expire unsent user data.
Note: the separate bullpen SQLite path HAS been substantially repaired (see below).

R04 HIGH — Coach planner cache remains shared across accounts.
Evidence: plannerStore.js:12-14 uses global plan/template/custom-drill keys;
listPlans(null) returns all rows. Player progress and player cache access now have
owner checks, but coach plans/templates lack owner namespacing. sessionTermination.js
clears auth/session keys only, and sessions.removeSession does not purge this cache.
Impact: shared-device coaches can see stale/shared drafts or templates, particularly
before team context resolves or for another coach on the same team. This is local
cache isolation, not proof of a server authorization bypass.
Fix: namespace coach caches by authenticated owner and team, quarantine legacy
unowned records, and test account switching offline.

R05 HIGH — Mobile Live AB edit calls the wrong route.
Evidence: screens/Statics/editPractice/EditLiveABScreen.js:439 sends
PUT /liveab/{resultUuid}; registered route is PUT /api/result/liveab/{uuid}
(routes/api.php:532). httpService uses the /api/ base and does not add result/.
Fix: use the existing authorized result endpoint; verify payload, reload edited
stats, and retain cross-team rejection tests. Do not add an unprotected alias.
Acceptance: edit a saved Live AB result on iPhone; web statistics reflect it.

R06 HIGH — Mobile password reset route and password policies disagree.
Evidence: More/RosterScreen/EditPlayer.js:305 posts players/{id}/set-password;
server registers coach/players/{id}/set-password (routes/api.php:317).
The screen's length check is 6 despite its label saying 8.
RegisterCoachRequest accepts 6+, RegisterPlayerRequest only requires password;
SetPlayerPassword accepts 6+, whereas LoginRequest requires 8-20 and
AccountDeletionController requires 8-128. AccountDeletionScreen disables verification
for passwords below 8. Accounts can be created/reset with passwords that later fail
login or deletion validation. The native invitation flow also enforces 8-20.
Fix: unify NEW-password policy across web/mobile/backend. Existing-password proof
must validate the credential rather than reject a legitimately stored password by
new length policy. Cover 6/7/8/20/21-character boundary cases. A fresh isolated run of the actual request password rules confirmed
lengths 6 and 7 pass both registration validators but fail login; length 21 also
passes both registrations and fails login. Lengths 8 and 20 pass all three.
No users were created in this reproduction.
Do not blindly fix the mobile route before reviewing R07.

R07 HIGH — Coach password override conflicts with player-owned claimed accounts.
Evidence: Api/Coach/SetPlayerPassword.php:36-59 permits a shared-team coach to
replace a player's password and revoke tokens without recipient proof, claimed-state
restriction or head-coach-only requirement. Shared membership is checked, so this
is NOT an unrelated-account takeover. The query also lacks actual=true on PlayerTeam.
Existing SetPlayerPasswordTest explicitly allows a coach to reset an existing user.
Risk: assistant/shared-team access can become full player account access, including
information beyond that team, once a player owns the claimed account.
Fix: define the intended ownership policy. Prefer recipient-controlled reset for
claimed accounts, and invitation setup for unclaimed profiles. Preserve strict
role/active membership checks and add claimed/assistant/former-member regression tests.

R08 HIGH — Automated production communications remain unverified.
Last supplied production evidence: enabled Plesk heartbeat remained at 01:00 UTC
when server time was 03:37 UTC on October 17. Direct develop cron heartbeat also
failed; Run Now worked. This is evidence of a scheduling problem at that time,
not proof it is still broken today. No administrator repair evidence was supplied.
Local Kernel schedules communications-dispatch every minute and weekly-progress
Monday 08:00 in app timezone. Workers and Laravel schedule:run are separate needs.
A heartbeat alone does not generate scheduled reports; a worker alone does not
schedule outbox dispatch. Current communications-status/probe command exists locally;
its production installation was previously absent and has not been reverified.
Release gate: automatic harmless worker probe and scheduler heartbeat succeed without
Run Now; approved-recipient invitation, assignment and opted-in weekly report deliver
once. Keep pilot/category switches restricted until this passes. Review queued backlog
before expanding recipients. Do not recreate player profiles to test cron.

R09 HIGH — Dependency/security maintenance needs explicit release triage.
composer.json still requires Laravel 9; official security support ended 2024-02-06.
Composer production audit reports advisories for Laravel, Guzzle, CommonMark,
Flysystem and Symfony HTTP Foundation. Full audit additionally includes dev tools.
Mobile npm audit --omit=dev reports 47 affected package entries (1 critical,
37 high, 9 moderate). Some build tooling remains in the production dependency tree;
this DOES NOT mean all advisories execute in the shipped app. Web full npm audit
reports 27 affected package entries (2 critical, 15 high, 10 moderate), including
Vitest/dev-server tooling. Axios is flagged in both trees. Counts are package entries,
not confirmed exploitable application vulnerabilities.
Existing RejectEmailHeaderInjection is a compensating control, not a supported
framework replacement. Distinguish Node adapters/dev servers from browser/RN paths.
Fix: record advisory reachability and safe lockfile updates; upgrade unsupported
framework/tooling with dedicated regression coverage. No npm audit fix --force or
unplanned Laravel major upgrade was performed. Do not blindly follow the old upgrade
document's feature-branch instruction; current user requires the existing main branch.

R10 HIGH / POLICY GATE — Age eligibility differs between invitation and registration.
InvitationEligibility blocks under-13 and unknown/invalid DOB, and no guardian
relationship/consent implementation is present. However public player/register uses
RegisterPlayerRequest (born is merely required/date) and RegisterPlayerController
creates the account and token without invoking InvitationEligibility.
Fix: have product/privacy owners define one approved policy for self-registration,
coach-created profiles and claiming; enforce it consistently with backend tests.
Do not advertise all-age self-service onboarding based solely on invitation safeguards.
This finding is a technical inconsistency, not a legal-compliance determination.

R17 HIGH / PRIVACY GATE — Account deletion misses current schema and communications data.
AccountDeletionService.php:111-113 attempts to clear players.born, but the actual
column is players.born_date (Player.php and 2022_08_15_174112_create_players_table.php).
The helper silently filters out nonexistent columns, so DOB is not cleared by that
operation. The service does not address team_invitations or communications tables,
and CommunicationObserver has no deletion hook. Invitation email addresses and
historical delivery payloads therefore require explicit retention/anonymization review.
Pending acceptance is still rejected for a deleted user by eligibility checks; this
is not a claim that a deleted account can be accepted. However invitation hashes/
state are not explicitly revoked here, and InvitationService.send (:83-92) can reject
a replacement invitation because an old accepted invite still matches the same email
and team. This explains why prior test cleanup needed extra invitation handling.
Fix: expand the deletion inventory to actual field names and new tables; revoke
credentials, cancel pending deliveries, and anonymize/delete retained personal content
according to an approved retention policy. Preserve only justified minimized history.
Acceptance: create DOB, accepted/pending invitations and delivery payloads, delete
through the REAL API, then inspect retained fields, reject old tokens, and test a
fresh authorized account invitation without old-ledger interference. No production
records were inspected or deleted in this audit.
