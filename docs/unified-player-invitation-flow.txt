FMTRX unified player invitation flow

Audit
Worked on existing fungoweb/main, initially clean. The public
/invitations/accept route already uses the existing Laravel invitation ledger,
identifies the existing player/team from a hashed token or code, and accepts
without a team code. The acceptance service never creates a player. Password
setup updates the invited record; existing accounts require password or a
matching authenticated account. Acceptance returns /player-dashboard. The
frontend reuses standard login and its HttpOnly web cookie. Pending invitation
registration routes already return to acceptance instead of creating a new
player. No backend authorization changes were needed.

Gaps fixed
Player login defaulted to legacy team-code claiming, causing confusion during
invitation sign-in. It now defaults to email login; Use a team code remains an
explicit option. The invitation screen saves email/manual code only in module
memory during SPA sign-in, just as the secure link token was already retained.
The continuation path (without secrets) is saved in sessionStorage. New links
clear old drafts, and malformed new tokens cannot reuse a previous token.
Explicit team-code fallback clears the invitation continuation. Completion
clears the in-memory credentials. Reloading requires reopening the invitation
email or entering the backup code; tokens are not persisted to support reload.

Copy now recommends Claim Profile, explains no team code is needed, and directs
new invitees to choose a password on the existing-profile setup screen instead
of registering again. Error guidance covers invalid, expired, revoked and
already-used invitations without exposing private invitation details. Accepted
and revoked hashes remain erased; we do not weaken that protection to reveal
which unavailable state a submitted secret previously represented.
