Release blockers / gates
------------------------
B1 — Invitation expiry is unsafe under older MariaDB timestamp defaults.
Evidence: generated Laravel DDL from all THREE communications migrations was executed in an isolated mariadb:10.1.48 container. All five tables and their indexes were created successfully. However, with explicit_defaults_for_timestamp=OFF (container default), team_invitations.expires_at became:
  timestamp NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP
A synthetic invitation expiring 2026-12-01 00:00:00 changed to 2026-10-16 22:47:15 when only delivery_status changed from queued to sending. Both worker updates can shorten expiry to the current instant. Acceptance can then reject a freshly emailed invitation.
Source: database/migrations/2026_10_16_180000_create_team_invitations_table.php, timestamp('expires_at'); app/Jobs/SendTeamInvitation.php updates delivery_status/token/sent_at.
Recommended correction: use an explicit non-auto-updating DATETIME for expires_at. If already migrated anywhere, use an additive corrective migration; changing only the original file will not repair that database. Review existing invitation expiries; do not silently revive expired tokens. A separate isolated proof replacing only this column's DDL with DATETIME preserved the future expiry during the same update. This correction was NOT applied to the application during the audit.
Production must still report its exact VERSION(), column definition and explicit_defaults_for_timestamp. Prior reports point to MariaDB 10.1; no live server was inspected. Passing local MySQL 9.6 tests does not remove this blocker.

B2 — No technical control for the proposed recipient/category pilot.
config/communications.php provides engine, send, weekly and invitation flags. There is no pilot recipient/team allowlist and no individual workout/assessment/development/billing send gate. Turning SEND_ENABLED=true permits every eligible pending delivery. INVITATIONS_ENABLED=true enables all authorized team coaches, independent of SEND_ENABLED. Weekly is independently gated and opt-in; the other optional categories default on.
Before a production-only-test-accounts pilot, add recipient/team restrictions checked at both creation and send time, plus category gates for the staged rollout requested. Alternatively validate on an isolated staging deployment containing only approved test accounts; do not portray the current global switch as a restricted production pilot. Existing captures/backlogs must be reviewed before activation. Do not manipulate real users' preferences to simulate rollout controls.

B3 — Logged-out email destinations are lost on sign-in.
resources/router/index.js beforeEach returns '/' for unauthenticated protected routes. It does not preserve to.fullPath. Existing login flows route to dashboards. Email origins/paths are correct, but a logged-out workout/report/settings click can lose its date, plan ID or selected assessment. Add a same-origin allowlisted intended-destination flow through login, with role/permission revalidation and open-redirect tests. Invitation acceptance has its own public flow and is not this particular issue. Gate broad mail activation on browser acceptance of the complete logged-out link path.

B4 — Youth invitation/consent policy is unresolved before a youth rollout.
InvitationService.accept contains no DOB gate; the existing tests deliberately allow a player born in 2014 and unknown DOB, matching the user's earlier all-age decision. RegisterPlayerRequest collects DOB but does not establish guardian authority or parental-consent records. There are no guardian accounts, child links, delegated access or consent/revocation records in this implementation. Possession of a player email invitation verifies that mailbox for acceptance; it does not establish parental consent.
FTC guidance covers child-directed services and operators with actual knowledge of collecting personal information from children under 13, generally requiring notice and verifiable parental consent with limited exceptions. This is not a blanket US rule that all under-18 users need the same workflow. Applicability, audience, jurisdictions and any existing off-platform consent need qualified privacy/legal review. The all-age product instruction and coach/team membership alone are not evidence of that review. Define a verified consent/account policy, retention/deletion and parental access process before activating affected youth invitations. The code's age behavior was preserved during this audit.
Source: https://www.ftc.gov/business-guidance/resources/complying-coppa-frequently-asked-questions
Also review the amended rule linked by the FTC: https://www.ftc.gov/legal-library/browse/rules/childrens-online-privacy-protection-rule-coppa

B5 — Production infrastructure and device acceptance remain unverified.
The actual Plesk domain PHP CLI path/version, DB version/column definitions, existing jobs table, cache driver, Supervisor permissions, running workers and cron entries were not inspected. A real device/browser pilot was not performed. These are deployment/activation gates, not claims of discovered production failures. The server previously reported QUEUE_CONNECTION=sync; leaving it sync is incompatible with the invitation and outbox dispatch guards. Read-only preflight plus a production-shaped rehearsal must precede migration approval.

Nonblocking improvements / follow-up defects
--------------------------------------------
N1. Invitation email validation accepts 254 characters while Schema::defaultStringLength(191) makes team_invitations.email VARCHAR(191), as confirmed against the local test schema. Align API limits with actual user/invitation storage, or deliberately migrate both. Current long valid addresses can fail at persistence instead of returning validation errors. Ordinary addresses are unaffected; no promise of full 254-character support should be made.
N2. Invitation workers recheck inviter/team but not the target player's active roster/account state immediately before sending. Acceptance does recheck and rolls back a removed player. Add the send-time check to suppress a queued invitation after removal/account closure; otherwise stale mail can reveal team/coach names and offer an unusable link.
N3. Outbox polling can enqueue the same pending job repeatedly while workers lag. Row locks and unique delivery keys prevent repeat automatic mail attempts, but duplicate jobs waste capacity. Consider queue uniqueness/leases and queue-lag alerts before large rollouts.
N4. Remote delivery is not exactly-once. 'sent' means transport acceptance, not inbox delivery. 'unconfirmed' and stuck 'sending' require manual provider review, not blind retry. Provider message IDs and delivery/bounce webhooks would improve operations. Invitation provider exceptions are sanitized; outbox processing errors are generic. Protect any upstream exception/debug logs as well.
N5. Coach delivery UI shows only the most recent 25 records; inbox access filtering can produce empty pages with historical totals. Improve pagination and readable recipient labels without exposing cross-team data.
N6. Weekly counts depend on recorded completion timestamps; submissions do not prove every drill completed. Reports use application timezone and current membership, not historical roster snapshots. Global player fitness data follows existing intelligence behavior; do not represent it as measured exclusively by this team.
N7. CI currently migrates MariaDB 10.6 and does not run the PHP feature suite. Add a supported test matrix/rehearsal for the actual production engine and runtime. The modern local database did not expose B1. Maintain a separate platform upgrade plan for the old production stack.
N8. Existing ApexCharts chunk remains ~501 KiB; Vite emits the >500 KiB warning but the build succeeds. This is not a communications release blocker.

Integration / authorization findings
-------------------------------------
- No duplicate definitions found for the communications tables or effective method/URI routes. Three migration files create five tables: team_invitations, jobs, communication_preferences, communication_events, communication_deliveries. failed_jobs predates Phase 2. Check for manually created production jobs tables before applying anything.
- One CommunicationObserver registration per observed model in AppServiceProvider. Event discovery is disabled; legacy UserCreated/UserChanged/SentResults listeners handle SMS, not a second copy of these emails. Invitations retain their own ledger/job and are not duplicated into the generic outbox.
- Daily-plan publication and new assignments can both record events, but delivery keys collapse the same initial plan/player. Ordinary edits do not resend; explicit update notification is once per version. Program batches dedupe by program/player. Raw SQL/bulk writes bypass observers and need explicit event recording in any future import paths.
- Weekly commands require engine+weekly flags and per-user weekly_reports=true. Unique team/week/recipient event and delivery keys prevent rerun duplicates. Send-time preference checks suppress opt-outs made after queuing. Scheduler withoutOverlapping alone is not the dedupe guarantee; the database keys are.
- RevenueCat checks the provider authorization before processing; provider-event uniqueness/locking and notification dedupe protect retries. Sync notifications require meaningful verified before/after changes. Active-period cancellation is distinguished from expiration. Existing entitlement behavior is preserved.
- Public invitation inspect returns validity/expiry only; acceptance requires token, correct email and identity/password checks. Tokens are hashed, rotated and single-use; raw tokens are not queued. Team/user/invitation locks protect acceptance. Existing users/profiles are retained, not copied or merged.
- Coach requests use Sanctum coach ability, route scope and membership authorization; coach invitations additionally require head-coach authority. Preferences/inbox are self-only and claim-only tokens do not gain access. Communication delivery rechecks resource assignment and current team access.
- Public acceptance: 5/minute; inspect: 20/minute. Invitation writes: 10/minute, resend: 5/minute. Announcements and explicit workout updates: 5/minute. Preferences: 20/minute, mark-read: 30/minute. API-wide throttling also applies. Distributed production throttling needs a shared working cache; confirm proxy/IP configuration.
- New action links use strict https://app.fmtrx.com and existing frontend paths. Assessment URLs contain opaque IDs, not measurements. The authenticated report applies existing access checks. The link-origin checks do not solve B3.
- New flags default false in both config and .env.example. These switches do not disable pre-existing password-reset/security mail or SMS. There is no global guarantee of "no email anywhere" from a communications flag alone.
- No marketing consent system or guardian access is implied. Invitation email possession is recorded on that invitation, not used to blanket-verify historical accounts.

Rollback / stop procedure
---------------------------
- First disable INVITATIONS_ENABLED, COMMUNICATIONS_ENABLED, COMMUNICATIONS_SEND_ENABLED and WEEKLY_REPORTS_ENABLED. Rebuild config with the verified PHP binary. Restart workers so they load it. A send already in flight cannot be recalled.
- For immediate containment, stop only the dedicated communications worker: sudo supervisorctl stop 'fmtrx-communications:*'. Leave default processing running if unaffected. Do not delete queued/failed jobs or delivery records to hide the incident.
- Cancel/remove only the new scheduler entry if required; preserve pre-existing schedules. Document whether disablement has suppressed invitation jobs that now need explicit resend.
- If rolling back code, keep additive tables/data. Restore the previously approved release using the deployment system, then rebuild config and restart compatible workers. Old code that lacks these job classes must NOT consume their queued jobs. Keep communications worker stopped until code/data compatibility is reviewed.
- Never migrate:rollback an arbitrary batch containing production invitations, preferences, delivery history or accepted account changes. Do not undo profile ownership or delete users to reverse invitation acceptance. DB restore is a separate emergency decision because it would discard intervening workouts/accounts.
- Before reactivation inspect pending/sending/unconfirmed/suppressed records, verify provider state, and approve any resend deliberately. Pending capture-mode records are still eligible later. Disable flags first; do not silently switch to sync as a substitute for stopping asynchronous work.
