Laravel authentication audit
-----------------------------
- routes/api.php POST login uses LoginController and LoginRequest. LoginRequest requires email/password (8–20 characters); AuthUtils also has a password-authenticated phone fallback.
- LoginController records last_login_at and user_login_history, creates a Sanctum token, returns role-specific resources and server-issued administrative capabilities.
- Web clients send X-FMTRX-Client: web and receive the secure HttpOnly SameSite=Strict fmtrx_api_token cookie; native clients receive the token in the existing response data.
- Team invitation acceptance validates the link/code, recipient, identity, age and roster then completes an existing placeholder in place. This is not six-digit email login.
- No six-digit email-login request/verify endpoint was found in the audited auth routes/controllers/security services. Existing password reset and invitation emails are not interchangeable login mechanisms.
- Resend is already the configured default mail transport, using notifications@mail.fmtrx.com and FMTRX. Reuse it, Laravel mail/notifications, and the supervised asynchronous queue. No new provider/key is needed.
- Current AuthUtils password lookup does not explicitly include status in its credential predicate. A new method must explicitly check active/nondeleted/eligible account status and administrative capability, while any change to the old password policy must be separately reviewed and tested. This audit does not alter existing login behavior.

Proposed additive six-digit email sign-in — NOT implemented
----------------------------------------------------------
Keep POST login and both existing password UIs working. Add a separate Email me a sign-in code option, initially behind OFF flags and exact-recipient pilot controls. This proves access to a mailbox; do not label it MFA or guardian consent.

Initial scope: existing active, claimed, non-administrative player/coach accounts. For players recheck confirmed age 13+; do not let OTP bypass invitation youth restrictions. Unknown email does not create a new account. Unclaimed placeholders must complete the invitation workflow first, so email login cannot bypass membership/claim controls. A future entirely passwordless placeholder-completion flow requires its own reviewed restricted-auth design; current claiming still requires choosing a password for a placeholder.

Suggested endpoints:
  POST /api/auth/email-code/request {email}
  POST /api/auth/email-code/verify {challenge_id, code}
Return the same generic request message and response shape for existing/unknown/disabled/ineligible recipients, including an opaque challenge reference. Avoid account-existence leaks via timing, differentiated errors or retry behavior. Requesting a code must not lock out normal password login.

Suggested security defaults, to validate in implementation:
- Cryptographic random six-digit string, including leading zeroes; five-minute expiry, single use, purpose email_login. Not a team/invitation/recovery code.
- Separate short-lived login-challenge state with random ID, user reference when eligible, normalized email snapshot, generation, keyed HMAC digest, expiry, attempts, delivery/used timestamps. Use MariaDB-compatible DATETIME fields. Do NOT put six-digit codes in team_invitations or use plain SHA-256: the small code space is vulnerable to offline enumeration without a separate server-held key. Use domain-separated HMAC and constant-time comparison with a securely managed key.
- Five attempts per challenge plus aggregate account/IP budgets across resends; sixty-second resend cooldown and an initial three-requests/15-minutes account budget. Add IP limits to constrain mail bombing and distributed guessing; tune without revealing account state. Rate-limit keys must not disclose raw emails in logs. Resend rotates the generation/code and invalidates previous challenges; it must not reset aggregate abuse limits.
- Lock and consume the challenge atomically. Recheck email, account status, age/capabilities and expiry at verification. Two concurrent verifications can issue at most one successful authentication result.
- Queue only challenge ID/generation. Delivery worker rechecks feature/pilot gates and eligibility, generates the code in memory, writes its digest/expiry and sends through existing Laravel mail. Drop stale generations and expired queue work. Raw codes must not enter queue payloads, logs, analytics, browser persistence or native offline storage. An uncertain provider result must not lead to blind automatic sends/regeneration; the user may request a new challenge under the cooldown.
- On success reuse a shared authenticated-session response service extracted from LoginController, with regression tests proving password login is unchanged. Reuse Sanctum abilities, cookie/native-token distinction, administrative capabilities and login auditing. Do not create or relink users; do not modify password, subscriptions or player history.
- Suggested new flags FMTRX_EMAIL_LOGIN_ENABLED=false and FMTRX_EMAIL_LOGIN_SEND_ENABLED=false, using the existing strict pilot allowlist during rollout. These are proposals, not added environment variables. Verify flags at request, delivery and verification. Preserve existing password-reset/security mail behavior. Optional workout-mail preferences must not unexpectedly control user-requested login codes.
- Show numeric keyboard/one-time-code autofill in the app and autocomplete=one-time-code on web, preserving leading zeroes. Clear entered codes on completion. Keep password fallback visible and preserve validated intended destinations.

External guidance consulted for the proposal (not implementation claims)
-----------------------------------------------------------------------
OWASP's Forgot Password Cheat Sheet recommends consistent request responses, secure random single-use expiring credentials, secure storage and per-account abuse controls. Applying these properties to a separate login-code flow is a design recommendation, not a claim that password-reset guidance makes email login MFA:
https://cheatsheetseries.owasp.org/cheatsheets/Forgot_Password_Cheat_Sheet.html
Resend supports idempotency keys for send retries. This can help transport deduplication, but does not replace application single-use state or make email delivery exactly once:
https://resend.com/changelog/idempotency-keys
