Exact database defect and repair
--------------------------------
MariaDB 10.1.48 with explicit_defaults_for_timestamp=OFF implicitly converted the original expires_at TIMESTAMP into DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP. Updating delivery_status shortened an invitation's expiry to send time.
The original creation migration now uses DATETIME. A NEW additive migration, 2026_10_16_200000_fix_team_invitation_expiry.php, changes already-installed expires_at columns to DATETIME NOT NULL. It preserves all stored values, including already-shortened expiry; it does not revive tokens. Affected expired invitations need an authorized explicit resend after review. down() intentionally retains the safe type.
There are now FOUR communications migration files, not three. The three base migrations still create five tables; the fourth corrects expiry. On previously migrated databases only the pending correction is required. Never fake migration history or regenerate queue tables.

Pilot controls and queue behavior
---------------------------------
Both SendTeamInvitation and SendCommunicationDelivery check the global engine, global send flag, category, and current normalized recipient allowlist immediately before dispatching a notification. Invitation workflow and weekly-generation flags are additional gates. Disabled jobs leave their pending ledger state intact and send nothing. Existing authentication/password-reset emails are outside these controls and remain unchanged.
The outbox dispatcher filters disabled categories and recipients BEFORE applying its batch limit, preventing disabled backlog from starving the pilot. ProcessCommunicationEvent and SendCommunicationDelivery now use unique queue locks (one-hour lease); existing database unique keys and transactional checks remain the final deduplication protections. Use a persistent cache shared by the relevant workers. A provider call is not an exactly-once transaction: sending/unconfirmed records require provider review rather than blind retry.
Paused outbox deliveries can be picked up by polling after reactivation. A paused invitation job has been consumed and requires a deliberate reviewed resend; it is not automatically replayed. Review all pending records before activating a category. An in-flight transport request cannot be recalled. Long-running workers must be restarted after configuration changes; flags are not a remote live cancellation service.

Authentication and account continuity
--------------------------------------
An allowlisted relative destination, including permitted date/plan/assessment parameters, survives SPA sign-in in sessionStorage for up to 30 minutes. External/protocol-relative paths, unapproved pages/parameters, fragments, whitespace and token parameters are rejected. Existing role/resource authorization still applies after navigation.
Invitation token stays in module memory only through SPA sign-in; the fragment is stripped from history. It is never persisted in sessionStorage/localStorage. A hard refresh or a different browser requires reopening the email. Player and coach login links return to acceptance. Pending invitations divert ordinary registration links back to acceptance so a placeholder athlete is completed in place instead of being independently registered again. New coaches use existing inline invitation creation. Existing/new player registration login destinations use the same helper.
The current invitation flow has no separate mandatory email-verification route to bridge; possession of the invitation is checked by existing acceptance. This repair does not bypass or add authentication verification rules. Any future full-page verification flow needs its own safe continuation design.
Twelve frontend tests cover safe destination retention/consumption, rejection of unsafe inputs, expiration, storage failures, and in-memory token continuity. PHP tests cover expired/revoked/rotated invitations, identity safeguards and preservation of historical player records. These are automated checks, NOT a completed browser/device journey.

Youth restrictions
------------------
The existing Player.born_date is the source of age. Under-13 players cannot be invited, resent, sent a queued invitation, or accept an invitation until an approved guardian workflow exists. Missing/invalid/future DOB also blocks invitation eligibility pending coach review. A player exactly 13 is eligible under this technical gate; 13–17 is not treated as under 13. Coach profile creation/management is unchanged.
No guardian account/link/verified-consent policy was found or added. No checkbox was added. Before under-13 invitation activation, define guardian identity verification, relationship/access permissions, consent evidence/revocation, parent access/deletion, and applicable regional policy with the responsible owners. The age gate is not a claim that the entire application meets all youth privacy obligations. Existing general registration and historical accounts were not reworked by this focused repair.

Other corrections
-----------------
Invitation API/UI email limits now match existing VARCHAR(191) storage; overlong addresses fail validation. Send-time eligibility rechecks player account status, email, active roster membership and age; coach invitations recheck known target accounts. Stale invitations are suppressed and explicit resend revalidates eligibility. Coach UI explains disabled/pilot sending and DOB requirements. One account-data console log was removed from login.

Rollback / emergency stop
-------------------------
Stop dedicated communications workers first for immediate containment:
   sudo supervisorctl stop 'fmtrx-communications:*'
Set global send/engine and all category flags false. Disable invitation workflow too if acceptance itself needs pausing; otherwise a send-only stop can leave already-issued valid acceptance available.
   "$FMTRX_PHP" artisan config:cache
   "$FMTRX_PHP" artisan queue:restart
An in-flight email cannot be recalled. Preserve queue payloads and delivery records; do not queue:flush or blind-retry unknown provider outcomes. Restore the prior approved code artifact only after checking queued class compatibility; keep communications workers stopped if it lacks these classes. Keep additive tables and the DATETIME correction. Do not run migrate:rollback: it can delete invitations/preferences/outbox history. Do not undo accepted account links or delete player records. Full database restore is a separately approved recovery decision because it loses intervening data. Review paused invitations for explicit resend and pending outbox for eligibility before reactivation.
