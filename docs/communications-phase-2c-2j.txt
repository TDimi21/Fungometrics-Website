FMTRX Communications Phase 2C–2J
Implementation and deployment review — 2026-10-16

Scope and architecture
----------------------
Implemented on existing fungoweb main. No commit, push, deployment, production migration or real email was performed. Existing Phase 2A/B audit and invitation flows are in communications-phase-2.txt; its "future phases" paragraph is superseded by this document.

Laravel 9.52.21, PHP requirement ^8.1; tested locally on PHP 8.2.30. Existing Resend Laravel integration, Notifications, Markdown branding, authentication and queue drivers are reused. No Composer/npm dependency or lockfile change is required.

Existing authenticated player identity is users.id. DailyPlanAssignment.user_id, PlayerAssessment.user_id, FreeAssessmentResult.player_id, PlayerTeam.user_id and CoachTeam.coach_id are used through their existing relationships. No player/profile merging, session/statistic changes, or new billing entitlement rules are introduced. Guardian accounts/links do not exist; no guardian delivery is inferred. Previously approved all-age invitation policy remains unchanged.

The shared observer records events using the same DB connection as the saved model. Existing enclosing transactions also contain the event write. Workers poll committed events, resolve current recipients and record unique deliveries. Sending rechecks active account, email, assignment/resource access, current team membership and optional preferences. HTTP requests do not perform bulk mail delivery. Direct query-builder/import SQL bypasses Eloquent observers: future import code must explicitly call CommunicationOutbox::record after saving the relevant records.

Event mapping and deduplication
-------------------------------
CoachRegistered: completed coach user creation, or initial password completion; one welcome per account.
PlayerInvited / CoachInvited: existing Phase 2B InvitationService, SendTeamInvitation and team_invitations delivery/status history remain authoritative. They are not duplicated into the generic outbox. Coach selects existing player/email or invites coach with explicit permissions, resends/revokes through existing UI. Recipient accepts the hashed, expiring, single-use token through the existing frontend; atomic identity checks preserve history and prevent duplicate membership.
WorkoutAssigned: published DailyPlan and newly created assignments; one initial delivery per plan/player. Drafts are silent. Ordinary edits are silent. Explicit coach notification uses the current saved version and confirmation, once per version.
AssessmentCompleted: completed FreeAssessment with report_snapshot, participant membership and recorded results; newly saved PlayerAssessment (AssessmentDraft is separate). One initial notification per assessment/player. Public URLs contain only resource IDs, never report measurements; report authorization is unchanged.
DevelopmentPlanPublished: published WorkoutProgram schedule and its published daily plans; one delivery per program/player. Later publication batches can reach newly assigned players without resending to existing recipients. Link opens the player's workout dashboard, where the actual assigned program workouts are delivered.
WeeklyProgressReady: one completed Monday–Sunday week per opted-in account/team. Monday 08:00 in application timezone. Empty reports are skipped. Players get dated session counts, workout submissions, relevant goals, velocity trends, strength/athletic tests, assessments and upcoming assignments. Coaches get team activity and upcoming plans, with dashboard access to individual detail.
SubscriptionStatusChanged: existing verified RevenueCat reconciliation audit, meaningful status/plan/period/cancellation changes. Repeated provider events are deduped. Billing sync now records an audit for its existing missing-subscription expiration operation. Entitlement behavior is unchanged. Cancellation with remaining active time is not described as expired.
TeamAnnouncement: authorized team coach explicitly submits a message; request UUID prevents HTTP retry duplicates. Intended for team operations, not marketing.

Data accuracy
--------------
Weekly summaries reuse PlayerIntelligenceService.daily_velocity_averages and benchmark_profile. Sample-weighted exit and general pitching averages compare only dated records from the report week and previous week. Explicitly tagged FB bullpen results supply a separate fastball trend; other pitch types are never relabeled as fastballs. No missing scores, percentile ranks or projections are generated.
Only Practice rows with is_completed=true and recorded finished timestamps count as completed sessions. DailyPlanProgress.completed_at is labeled a workout submission, not proof of completing every drill. Missing legacy completion timestamps cannot be reconstructed by this feature. Fitness comparisons show actual recorded dates/units, not assumed weekly improvement. Existing benchmark availability is linked to the development dashboard without inventing new scores. Reports use application timezone boundaries, not per-user timezone settings. Current membership/assignments are used when processing; this is not an immutable historical roster report.

New schema
-----------
database/migrations/2026_10_16_190000_create_communication_outbox.php creates:
- communication_preferences: per-user optional email categories; weekly_reports=false by default.
- communication_events: unique event key, resource, team/recipient, payload, processing attempts/status.
- communication_deliveries: unique event/resource/occurrence/recipient/channel key, recipient/player/team, payload, pending/sending/sent/suppressed/unconfirmed state, created/attempted/sent/read timestamps and sanitized failure code.
Payload storage uses LONGTEXT with model array casts for older MariaDB compatibility, not native JSON columns. No existing application table is replaced. The jobs table migration is already part of Phase 2B; do not generate another queue migration.

Write routes are rate-limited. Foreign records and removed assignments are not exposed. Existing responsive mail.fmtrx-notification branding is reused with optional settings links. No app-native UI or push-notification channel is added; the authenticated endpoints are available to both clients.

Delivery semantics and limits
-----------------------------
- All feature flags default false. Disabled communications do not record historical actions or backfill them automatically.
- With engine enabled and sending disabled, workers can populate inbox/delivery records without sending emails. Those pending records WILL become eligible when sending is enabled; review them before activation.
- Unique database keys and row locks prevent repeated jobs from making duplicate automatic send attempts.
- Event processing errors retry through polling up to five attempts, recording only processing_failed. Monitor exhausted records.
- A provider exception results in unconfirmed/provider_delivery_unconfirmed. A process killed during send can leave sending. These states are NOT automatically retried: the provider may already have accepted the email. Review provider records and delivery IDs before any deliberate resend. This is not an exactly-once network delivery guarantee.
- sent means Laravel transport accepted the send; it does not prove inbox placement, opening, or bounce status. No provider delivery-webhook integration is claimed.
- Essential account/security, invitation and verified billing emails are separate from optional preferences. Weekly requires opt-in. No marketing subscription or consent is introduced.
- Existing invitation gate is independent from the new engine/send gates. To stop all communications, disable invitations too.
- Mail payloads contain private training summaries. Restrict database/admin/log access; raw provider errors/credentials are not saved in delivery records.
